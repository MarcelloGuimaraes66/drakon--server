Implementar nesta fase:

A. Comandos do agente Linux
Garantir que o binário perceptrum-agent suporte, de forma funcional e segura:

1. --help
2. version
3. validate-config [--base-url <url>]
4. check-deps
5. status
6. healthcheck [--max-heartbeat-age-seconds <seconds>]
7. run
8. pair --pair-code <code> [--base-url <url>]
9. provision --base-url <url> --exe-token <token> --client-id <id> [--exe-id <id>] [--timezone <iana>]

Se algum desses comandos já existir, revisar e fortalecer.
Se algum ainda não existir, implementar no escopo mínimo seguro.

B. Configuração persistente
Implementar persistência local em APP_RUNTIME_CONFIG_ROOT para:

1. base_url;
2. client_id;
3. exe_id, se fornecido;
4. timezone;
5. estado de paired/provisioned;
6. metadados não sensíveis.

Regras:
- Não gravar exe-token em plaintext.
- Não gravar pair-code em plaintext.
- Não imprimir tokens em logs.
- Não imprimir tokens no terminal.
- Não salvar secrets se o secure store negar armazenamento.
- Se o usuário tentar provisionar com token e secure store não estiver disponível, falhar com erro claro e seguro.
- Permitir fallback plaintext somente com flag explícita já definida na Fase 2.

C. Pairing
Implementar ou preparar o fluxo:

perceptrum-agent pair --pair-code <code> --base-url <url>

Comportamento esperado:
1. Validar campos obrigatórios.
2. Validar base_url.
3. Se backend não estiver acessível, retornar erro funcional claro.
4. Se pair-code for inválido, retornar erro funcional claro.
5. Se pair-code for aceito pelo backend, persistir config não sensível e secret via secure store.
6. Não crashar quando backend estiver ausente.
7. Não bloquear indefinidamente.

Se não houver contrato backend claro ainda, implementar uma camada bem definida e documentada, com erro funcional explícito:
"pairing backend contract not available yet" ou equivalente.
Mas o comando deve existir e ser testável.

D. Provisioning
Implementar ou fortalecer:

perceptrum-agent provision --base-url <url> --exe-token <token> --client-id <id> [--exe-id <id>] [--timezone <iana>]

Comportamento esperado:
1. Validar base_url.
2. Validar exe-token obrigatório.
3. Validar client-id obrigatório.
4. Validar timezone se fornecido.
5. Persistir base_url, client_id, exe_id e timezone em APP_RUNTIME_CONFIG_ROOT.
6. Armazenar exe-token somente via secure store.
7. Se secure store não estiver disponível, falhar fechado, exceto com flag explícita de fallback.
8. Atualizar agent_health.json para paired=true ou provisioned=true quando aplicável.
9. Não expor token em terminal, log ou health JSON.

6. run deve ter caminho claro para futuramente chamar HeadlessService real.
7. Se HeadlessService atual for Windows-acoplado, criar adaptador Linux mínimo ou wrapper seguro, sem quebrar Windows.
